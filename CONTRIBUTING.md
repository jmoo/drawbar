# Contributing

This repository contains Rust tools for Clavia Nord instruments:

- `nord-format` decodes reverse-engineered file formats.
- `nord-usb` implements the USB vendor protocol.
- `nord-cli` exposes both libraries from a terminal.
- `nord-bits-derive` generates the bitfield implementations.
- `drawbar` is the desktop and browser application.

This is a public repository. Do not add personal information, secrets, agent
memory, private notes, private RFCs, or the private specimen corpus. If a fact
is needed to understand public code, state the fact in the public repository;
do not point at a private note.

The project is not affiliated with, authorized by, or endorsed by Clavia DMI
AB. Keep the trademark disclaimers in crate READMEs and generated docs.

## Research and copyright boundary

All reverse engineering is black-box work for interoperability.

- Do not decompile or disassemble Clavia software or firmware.
- Derive formats and protocol behavior from self-generated specimen files,
  captured USB traffic, public documentation, and hardware observation on
  instruments the researcher owns.
- Public or leaked documentation may be consulted. Its text and data still
  have licenses; consultation is not permission to copy.
- Do not copy code, tables, or data from GPL, unlicensed, or otherwise
  incompatible projects. BSD, MIT, and Apache sources require attribution.
- Do not commit factory presets, sample or piano libraries, firmware, files
  shipped with Clavia software, or other proprietary material.

Committed fixtures must be self-generated by this project's tools or from the
instrument panel. Proprietary specimens belong in the private `nord-corpus`
repository. The `corpus` Cargo feature and `NORD_CORPUS_ROOT` allow tests to use
that repository without making it a public dependency. The layout under
`crates/nord-format/tests/fixtures` is the public example.

## What good code looks like here

Correctness starts at the boundary. Validate lengths, ranges, indices, echoed
addresses, protocol direction, and conversions where untrusted bytes enter.
Do not rely on debug assertions for conditions needed in release builds. Make
invalid generic parameters fail at compile time when Rust permits it.

Prefer code whose shape states the format or operation directly:

- tables and field declarations over repeated control flow;
- exhaustive matches over boolean state machines;
- one representation of a concept, named the same way in every crate;
- small values with enforced invariants over loosely related primitives;
- checked arithmetic at file, allocation, address, and time boundaries;
- an error over truncation, wrapping, silent fallback, or partial success.

Keep cyclomatic complexity low. Every branch is another state that must be
understood and tested. Split a function when its parts have distinct contracts,
not merely to reduce its line count. Prefer early returns for invalid states and
keep the successful path visible. Delete duplication before inventing an
abstraction, and delete dead flexibility instead of maintaining options no
caller uses.

Consistency is a feature. Follow the vocabulary, error behavior, ordering, and
ownership patterns already used by the relevant crate. Similar operations
should have similar signatures and failure semantics. Deterministic output must
not depend on hash iteration order or the incidental order of prior events.

Avoid speculative machinery. A dependency, trait, cache, background task, or
configuration switch must solve a current problem. Prefer the standard library
and existing workspace dependencies. More code is more surface for bugs.

### `nord-format` is declarative

Format modules describe bytes. Keep offsets, widths, encodings, and structure
visible in declarations. Do not bury a field layout in procedural control flow
when a table, type, or derive can express it.

The round-trip invariant is load-bearing: decoded objects are views over a
verbatim body, and bits claimed by no field survive untouched.

```text
to_bytes(from_stream(input)) == input
```

Do not trade byte-exact round trips for a tidier object model. An edit should
change only the bytes owned by the edited field. Unknown schema versions are
refused rather than decoded on a guess.

## Comments are liabilities

A comment consumes attention, can become false, and can stop the reader from
checking the code. Code must carry as much of its own explanation as its types,
names, and structure can bear. A comment earns its place only when removing it
would hide a contract, invariant, encoding, provenance, or hazard.

The default is no comment. The usual exception is one or two lines. Longer
module-level documentation is appropriate when it is the generated entry point
to a public API; a long comment inside implementation code is a request to
simplify the code first.

Good comments state:

- a non-obvious encoding: `// Perc speed stores 2/1/3 for soft/fast/both.`
- an invariant the type system cannot express;
- a correct-looking operation that is unsafe in a particular state, prefixed
  with `⚠️`;
- the provenance of a reverse-engineered fact.

Delete comments that:

- restate the next line or narrate the function;
- describe a previous implementation, a bug that was fixed, or work just done;
- justify this design by comparing it with discarded designs;
- announce a section that names and structure already make clear;
- repeat a test name or translate an assertion into prose;
- contain corpus counts or dates that will silently age;
- use emphasis, metaphor, or conversational filler in place of a fact.

Git records history. Private RFCs record extended design rationale. Neither
belongs inline as a story about the current code.

Use `///` for a contract a caller can rely on without reading the body. Use
`//` for a surprise encountered while reading the body. Do not turn an internal
essay into API documentation merely to preserve it.

Reverse-engineered claims use one of these exact provenance forms:

```rust
// Confirmed on hardware.
// Inferred from specimens; not confirmed on hardware.
// Unexplained: real programs hold this, and the panel cannot produce it.
```

Never drop the qualifier when moving or editing a claim. Arithmetic that shows
an encoding is evidence rather than a mutable measurement and may stay:
`// 43/127*10 = 3.39, and the panel reads 3.4.`

Review comments as code. Ask whether each one is current, actionable, more
precise than the implementation, and worth the context it occupies. Delete it
when the answer is no.

## Tests specify behavior

Apply the toilet test: a failure read in isolation should say what user-visible
behavior, invariant, or external contract broke. If the only diagnosis is
“output changed,” followed by inspecting a large diff and reblessing it, the
test is a change detector rather than a specification.

Do not add snapshots of debug output, generated field dumps, corpus census
results, current distributions, or other broad serializations of the present
implementation. Do not add a rebless workflow. Such tests resist harmless
refactors, approve accidental changes wholesale, and rarely identify a bug.

Prefer:

- compact input/output examples for an externally meaningful behavior;
- round-trip properties for every accepted file;
- mutation tests proving an edit changes only its declared bits;
- boundary and malformed-input tests for every parser and conversion;
- fault injection for cleanup, recovery, timeout, and partial-I/O paths;
- corpus sweeps that apply stable invariants to each specimen;
- small, hand-reviewed oracles for facts not derivable from the code under test;
- replay tests whose captured exchange is itself the external protocol evidence.

Exact-byte assertions are appropriate when the bytes are the contract: a known
wire frame, checksum vector, independently produced specimen, or minimal format
fixture. State the origin. Do not generate expected bytes with the same logic
being tested.

A test should contain enough information to distinguish a regression from an
intentional contract change. Test names state behavior. Assertions report the
relevant value and location. Helpers clarify setup but must not hide the claim.
Tests do not need comments that repeat those three things.

## Tooling and checks

This is a Nix-native project. Do not assume a tool is installed globally. Run
Cargo from `crates/` inside the development shell; the parent
`.cargo/config.toml` supplies the cfg needed by wasm builds.

- `nix develop -c cargo test --workspace` runs the default test suite.
- `nix fmt` formats Rust, Nix, TOML, and shell with the pinned tools.
- `nix flake check` checks formatting and evaluates every flake output.
- `nix build .#<crate>` builds and tests one crate.
- `nix build .#nord.all` covers every crate and cross target.
- `nix build .#nord.all-corpus` runs all suites against the pinned private
  corpus; `.#nord.<crate>-corpus` selects one crate.
- `nix build .#nord.all-corpus-full` uses the R2 corpus tier and requires a
  seeded store or R2 credentials. `.#nord.corpus` and `.#nord.corpus-full` are
  the corpus assemblies.

CI runs each crate with its declared `testFeatures`, rejects anything `nix fmt`
would change, and treats Clippy warnings as failures. The public suite must
compile and pass without private corpus access. `tests/corpus` discovers the
committed fixtures, plus the private corpus when enabled, and applies sidecar
`.oracle.json` files where present.

The CI corpus job runs the committed tier for in-repository pull requests and
gates publishing. It reads `jmoo/nord-corpus` through the read-only
`NORD_CORPUS_DEPLOY_KEY`; forks cannot receive that secret, so the job skips them.

Nix style is two spaces and alphabetized attribute-set keys. Use a dotted path
for one child (`a.b.c = v`) and braces for two or more children, decided per
attribute-set literal.

## Change discipline

Keep a change as small as correctness permits. Separate behavior changes from
mechanical cleanup when that makes either easier to review. Do not mix unrelated
format discoveries. Preserve user changes already present in a worktree.

Before declaring a change done:

1. Read the final diff, including tests and comments.
2. Check malformed, maximum-size, empty, timeout, and cleanup paths relevant to
   the change.
3. Verify round trips and field isolation for format work.
4. Run the narrowest useful tests during development, then the workspace suite,
   formatting, Clippy, and the applicable Nix builds.
5. Run corpus tests when the change touches decoded layout or protocol evidence.
6. Remove dead code, redundant tests, stale comments, and temporary diagnostics.

Refactors are behavior-preserving. The default suite and, where available, the
corpus round trip are the proof. Do not commit unless asked. When commits are
requested, use small logical commits and branch from `master`.

## Pull requests and releases

Pull requests are squash-merged to `master`, so history remains linear and the
PR title becomes the commit that lands. Every PR title is a Conventional Commit:

```text
<type>(<optional scope>): description
```

Allowed types are `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`,
`build`, `ci`, `chore`, `revert`. The scope is usually a crate name. `!` before
the colon, or a `BREAKING CHANGE:` footer, marks a breaking change.

Each crate's version lives only in its `Cargo.toml`. `scripts/bump.bash` derives
release levels from Conventional Commits since the crate's last release tag:
breaking changes bump major (minor for a 0.x crate), `feat` bumps minor, and
`fix`, `perf`, or `revert` bumps patch. Only commits touching a crate count; a
dependent of a bumped crate receives at least a patch bump.

The `bump` PR label runs `scripts/bump.bash --title` with the eventual squash
title, updates affected versions and dependents, refreshes `Cargo.lock`, and
pushes a release commit. It reruns on pushes and title changes and converges
from merge-base versions. Each crate takes the higher of the title's level and
the level required by its already-unreleased commits. For a fork, run the same
command locally. Running `scripts/bump.bash` without `--title` on `master`
catches up from release tags.

After the check, build, and corpus jobs pass on `master`, the release job runs
`scripts/release.bash`. Before publishing anything, it rejects a crate whose
version understates its commits since the last release; run `scripts/bump.bash`
on `master` to catch up. It publishes each crate whose version has no matching
`<crate>-v<version>` tag, then creates the tag and GitHub release. Dependencies
publish before dependents. Both release scripts accept `--dry-run` and are
idempotent.

Trusted Publishing cannot bootstrap a crate that has never been published.
Publish a new crate locally once; subsequent releases need no extra script
wiring.
